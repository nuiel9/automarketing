## 1. What the Meta MCP can and cannot do

`meta-devtools` is a **developer-operations** surface. Its eleven tools cover app
inspection, API health, webhooks, and documentation search. There is no Marketing
API, no ad creation, no creative upload — **it cannot craft or publish an ad**.
What it did here was research: read the app's real App Review and compliance
state, and search Meta's advertising documentation. The creative below is written
against `strategy.yaml`, not generated by the MCP.

## 2. Two separate paths — don't conflate them

**Running these ads manually, today: nothing blocks it.** The founder can create a
campaign in Ads Manager on their own ad account and paste this copy in. None of
the findings below apply to that path.

**Automating ads through the AutoMarketing backend: blocked, four ways.** Verified
on app `2057504731804808` (AutoMarketing) on 2026-08-10:

| Check | Result |
|---|---|
| `app_review.status` | `NO_SUBMISSION` — never submitted |
| `app_review.privileges` | `[]` — **zero** approved permissions |
| `app_review.requirements` | `has_privacy_policy: false` |
| `app_review.requirements` | `business_verification_passes: false` |
| `compliance.status` | `compliant`, no open violations ✅ |

The Facebook Page publishing that works today works because Development Mode lets
an app admin act on their own Page. That is not ads, and it does not generalise.

### Founder checklist to unblock the API path

Per Meta's Marketing API authorization docs, the "Create & manage ads" use case
requires `ads_management`, `ads_read`, and `business_management` — all three are
marked *required, cannot be removed* — plus the Marketing API Access Tier feature.

1. **Add a privacy policy URL** to app settings. App Review cannot be submitted
   without it. Nothing needs writing — eduverse.one already publishes one at
   `https://eduverse.one/th/privacy`; it just needs pasting into the Meta app.
2. **Attach and verify a business portfolio.** The app currently has none. The
   docs are explicit: an unverified portfolio can be added, but *"it must be
   verified before you can run ads."*
3. **Submit App Review** requesting the three permissions + Marketing API Access
   Tier.
4. Meanwhile, **develop against a sandbox ad account** — it needs no payment
   method, incurs no charges, and the ads it creates never run.

One ordering trap: Full Access tier requires 500 Marketing API calls in the last
15 days at <15% error rate. That's earned on Limited Access (auto-granted with
the Marketing API product), which the docs describe as *"for development only.
Not for production apps running for live advertisers."*

## 3. Targeting notes

Verified from Meta's targeting docs:

- `age_min` **defaults to 18**; if set explicitly it must be ≥13. `age_max` ≤65.
- Education is **not** a Special Ad Category. Those (housing, employment,
  financial products/services) bind advertisers based in or reaching the
  US/Canada/Europe — not a Thailand-targeted education campaign.
- Variant D mentions reading financial statements. That is financial *education*,
  not a financial product or service, so `FINANCIAL_PRODUCTS_SERVICES` should not
  apply. Worth a sanity check if the campaign is ever pointed at Europe.

⚠️ **One gap I could not close.** The TGAT/TPAT audience is mostly 16–18, and
Meta's API reference lists a **"Youth Ads"** endpoint whose documentation the
doc-search would not return. Meta does restrict what advertisers can use to
target minors, but I could not retrieve the current rule, so I am not stating
one. **Check the Ads Help Center before targeting under-18s.** The safe default
is to run Variant A at 18+ and reach younger students through Variant B, which
targets parents.

## 5. Links

`backend/app/utm.py` builds `utm_source={channel}&utm_medium=social&utm_campaign={slug}`
with slug `w{week}-{format}-{topic}`. These are **paid**, so `utm_medium` is
`paid_social` rather than the organic `social` — otherwise paid and organic
Facebook traffic land in the same bucket and neither can be read. Week 33:

```
A  https://eduverse.one/th/goals?utm_source=facebook&utm_medium=paid_social&utm_campaign=w33-ad-exam-prep
B  https://eduverse.one/th/goals?utm_source=facebook&utm_medium=paid_social&utm_campaign=w33-ad-parents
C  https://eduverse.one/th/goals?utm_source=facebook&utm_medium=paid_social&utm_campaign=w33-ad-university
D  https://eduverse.one/th/goals?utm_source=facebook&utm_medium=paid_social&utm_campaign=w33-ad-upskill
```

All four land on `/th/goals` — the goal box the copy describes. Sending them to
the homepage would break the promise the ad makes.

**Verified for logged-out visitors 2026-08-10.** `scenarios/goal-to-course.yaml`
logs in before navigating here, so it was worth checking that an ad-clicker with
no account isn't bounced to a wall. They aren't: `/th/goals` returns 200 and
renders the empty state — *"ยังไม่มีเป้าหมาย บอกคาวีสิว่าอยากไปถึงไหน"* — and
clicking **ตั้งเป้าหมายกับคาวี** opens the goal form in place, still on
`/th/goals`, with no login form shown. Signup is presumably required at submit
(not tested — submitting would create a real goal on production), but the ad's
promise survives the click, which is the part that matters.

## 8. Campaign one — the actual plan

For a **first** campaign, the goal is not sales. It is one clean read on whether
the goal→plan hook makes Thai people click. So: one audience, one creative, two
topics, one week. Running all four §4 variants at once splits the budget four
ways and teaches nothing.

### The decision: run to working adults

Campaign one goes to **working adults, 25–45**. Parents were the first call and
were reconsidered; both arguments are recorded here so the next campaign doesn't
relitigate this.

**The argument that decided it — decision-chain length.** A working adult sees
the ad, clicks, types their own goal, and uses the product in the same session.
One person, one decision. A parent clicks, gets interested, and then has to get
their teenager to actually sign up — and that second handoff is invisible to
you. If the parent converts and the child never does, the metrics read "the hook
didn't work" when what really failed was the handoff. Campaign one exists to
test the hook, so a second decision-maker corrupts the only signal it produces.
Seven days is also short: adult intent resolves inside that window, parent-child
conversations often don't.

**The parents argument, and why it was weaker than it first looked.**
`strategy.yaml` lists exam-prep students and parents first, and its Facebook note
says *"พูดกับผู้ปกครองได้ด้วย น้ำเสียงอบอุ่น"*. The supporting claim — "Thai
Facebook skews 30+, students are on TikTok" — is true but does **not** favour
parents: working adults 25–45 are on Thai Facebook in very large numbers too. It
argued for both audiences equally.

**What still points at parents, for later:** it sidesteps the unresolved Youth
Ads question (§3) by reaching exam-prep households without targeting a minor, and
TCAS season carries real emotional urgency. Run it as campaign two, when a
baseline exists and a longer conversion window is affordable.

⚠️ **Objective must be Traffic, not Conversions.** eduverse.one has **no Meta
pixel** — verified 2026-08-10, zero references to `connect.facebook.net` or
`fbq(` on the homepage. Conversions has nothing to optimise against and would
spend the budget blind. Installing a pixel is the prerequisite for campaign two,
and it's the single highest-value thing to add before spending more.

✅ **The UTM links ARE recorded — in Cloud Run request logs.** An earlier version
of this doc said attribution was impossible without app-side capture. That was
wrong, and it overlooked the obvious: the UTM is in the URL, so even though
eduverse-one never parses it, **Cloud Logging captures the full query string**
(`httpRequest.requestUrl`) with the client IP, retained ~30 days by default.

Attribution is therefore available **retroactively, with no pixel and no CAPI**:

```
# ad clicks
gcloud logging read 'resource.type="cloud_run_revision"
  AND resource.labels.service_name="eduverse-one-frontend-staging"
  AND httpRequest.requestUrl:"utm_campaign=w33-ad-ai"'   --project=eduverse-personal-krainat --freshness=3d   --format='value(timestamp, httpRequest.remoteIp)'

# auth events, same window
gcloud logging read 'resource.type="cloud_run_revision"
  AND resource.labels.service_name="eduverse-one-backend-staging"
  AND httpRequest.requestMethod="POST" AND httpRequest.requestUrl:"/api/auth/"'   --project=eduverse-personal-krainat --freshness=3d   --format='value(timestamp, httpRequest.requestUrl, httpRequest.remoteIp)'
```

Correlate on IP within a short window. Three things this method needs stated:

- ⚠️ **~59% of ad-URL requests come from Meta's own IP range `2a03:2880:…`** —
  prefetch and link-crawling, not people (296 of 500 over three days). Filter
  them out or every count is inflated.
- ⚠️ **`/api/auth/google` serves both signup and login**, so a match proves an
  *auth event*, not necessarily a new account. Confirm against the user table.
- ⚠️ **IP correlation under-counts.** Mobile clients change address between the
  landing and the signup, so misses are expected; matches are meaningful,
  absences are not.

**IPs are personal data.** This is reading your own server logs for attribution,
which is ordinary operational use — but do not build a persistent identity table
from it without revisiting the PDPA position in §2.

🔑 **`fbclid` is present in the logged URLs.** That is the ad-click identifier
CAPI needs to attribute a conversion back to the click, and it confirms the
approach recommended in the CAPI handoff is viable from data you already hold.

### The creative

`eduverse-ad-1080.png` — a 1080×1080 screenshot of eduverse.one/th, captured with
`app/video/shot.py`. Free: no AIVDO credits, no login, and none of the goal-leak
side effect the `demo` scenario has on the production account.

It's the right shape (1:1 = Facebook feed) and it shows the real product, which
is what `strategy.yaml` asks for — *"เน้นให้เห็นของจริงจากตัวแอป"*.

Two honest caveats: the image already contains its own headline and a
**เริ่มเรียนฟรี** button, which compete a little with the ad's headline and CTA;
and it carries a fair amount of text, which Meta no longer hard-blocks but still
tends to suppress. Both are acceptable for a first test. If CTR comes in weak,
the creative is the first thing to change — that's when the 11-second `motion_ad`
(5 credits) earns its cost.

**Do not use the dark "EDUVERSE — AI-Powered Learning Platform" banner.** It's
English, landscape, and generic enough to belong to any edtech company. It shows
the brand, not the product, and it cannot test the hook.

**ภาษาอังกฤษ — held back deliberately.** It is the biggest felt pain in Thailand,
which makes it tempting. Two reasons to wait: the ad space is saturated with
English schools, so you pay a premium to be one of many; and the product fit is
weaker. Eduverse builds structured courses with narration — strong for
decomposable knowledge like Excel or AI, weak for *conversation*, which needs a
practice partner. Promising fluency and delivering a course plan is a mismatch
you would pay for in bounces.

### Click path

You have to do this part — there is no API path today (§2), and account and
payment settings are yours to touch, not mine.

Either door works. **Business Suite → Promote → Create ad → Get website visitors**
is the simpler one; **adsmanager.facebook.com → Create → Traffic** gives the
placement control below. If Promote will not let you set manual placements, use
Ads Manager.

1. Confirm the ad account is **THB / Asia\_Bangkok** before anything else —
   currency and timezone are generally locked per ad account once set.
2. **Campaign name:** `w33-upskill-goalplan`. Leave Advantage campaign budget off.
3. **Ad set** — conversion location **Website**. ฿300/day, 7 days. Thailand,
   age 25–45, all genders, detailed targeting empty. Placements → **Manual** →
   Facebook Feed and Instagram Feed only.
4. **Ad 1** — Page **Eduverse.digital**, format **Single image**, upload
   `eduverse-ad-1080.png`. Paste Ad 1's text, headline, description. Website URL
   = the `w33-ad-ai` link. CTA **Learn More** — *not* "Apply now": there is
   nothing to apply to, and the mismatch costs you the click you paid for.
5. **Duplicate the ad**, swap in Ad 2's text and the `w33-ad-excel` link. Same
   image.
6. **Publish.** Meta reviews in roughly 24h.

### Result so far (2026-08-11, day 2)

✅ **The ad-level fixes worked.** Day-1 CTR was **0.85%** (34 clicks / 4,011

reads (99−34)/(7,071−4,011) = **~2.12%**, above the ~1.71% traffic and ~1.80%
education benchmarks. ฿183.31 spent, 99 link clicks, 79 landing page views at
฿2.32.

### Reading the result after 7 days

Compare the two ads first — that is what the campaign was built to tell you.

- **CTR ≥1%** — the hook works. Scale the winning topic, and run parents (§4 B)
  as campaign two.
- **CTR 0.5–1%** — copy is fine, creative is tired. Change the image before
  anything else; this is where the `motion_ad` earns its 5 credits.
- **CTR <0.5% on both** — the audience is wrong before the copy is. Move to
  parents rather than writing a third round of upskilling copy.
- **One topic clearly beats the other** — that is a product signal, not just an
  ad signal. It says what Thai working adults want from you.

If CTR is weak but one topic leads, vary **narrow vs broad** before changing
audience: both live ads name a specific goal, and it is untested whether the
specificity helps or limits reach.

Don't judge anything in the first 48 hours; Meta's learning phase makes early
numbers meaningless.
